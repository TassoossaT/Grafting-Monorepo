# `Grafting.Isekai.Protocol`

Generated FlatBuffers C# code for `Command`/`DomainEvent`/`Snapshot`
(master source §10.1/§10.2, DEC-013). No hand-written logic here --
`Generated/` is regenerated by
`pnpm exec nx run engine-domain-core:generate` (see
`libs/engine/domain-core/contracts/README.md`), gitignored, not the
source of truth.

## Current status

C-005/C-006 done: schemas generate and compile here (`dotnet build
dotnet/Grafting.Isekai.Protocol`). Deliberately **not** referenced by
`../Grafting.Isekai.Interop` -- neither project has a real consumer of
these types yet (`engine_submit_increment` still takes a plain `i64`,
not encoded bytes); wiring them together now would be scope creep ahead
of a real need.

References `Google.FlatBuffers` (NuGet) -- pinned to `25.2.10`, the
latest version actually published there, which lags the primary pinned
`flatc` (`tools/flatc-version.txt`, `25.12.19`). Generated C# embeds a
version-marker call the runtime package must match exactly, so this
project's `Generated/` output is produced by a second, older,
separately-pinned `flatc` (see
`../../tools/scripts/get-flatc-csharp.ps1`) -- not a workaround, the
actual fix for a real, confirmed cross-ecosystem publishing lag (see
`libs/engine/domain-core/contracts/README.md` for the full explanation).

Verified only by compilation here (`dotnet build`) -- the real round-trip
proof lives on the Rust side
(`libs/engine/domain-core/tests/flatbuffers_round_trip.rs`), since
nothing in C# consumes these types yet either.
