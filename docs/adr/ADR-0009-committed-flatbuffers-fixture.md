# ADR-0009: commit the C-006 evolution fixture's generated code

- Status: **Proposed.** Not a numbered Decision Gate of the master
  source; a narrow, structural exception to §10.3's default
  ("generated code ... does not need to be committed by default ...
  must be ignored when always reproducible"), recorded per that same
  section's own escape hatch: *"If a consumer or IDE requires committed
  code, the exception must be recorded via an ADR and validated with
  `codegen:check`."*
- Proposal date: 2026-07-28
- Decision date: pending — per this directory's own convention
  (`docs/adr/README.md`: "the Decision section may only be filled in by
  the project owner"), this section is left open for the owner, even
  though the surrounding code is already implemented and tested (the
  owner approved the C-005/C-006 implementation plan this ADR is part
  of; this file records the one piece of that plan that's a structural
  exception worth a standalone, explicit record, not a unilateral
  "Accepted").
- Related: master source §10.3 ("Generation"), §10.4 ("Evolution"),
  DEC-013 (`LOCKED`, FlatBuffers for structured data).
- Authority: in case of conflict, `GRAFTING_MASTER_SOURCE.md` prevails
  over this ADR.

## Context

C-006 ("Define schema evolution," master source §23) needs a *real*
compatibility test, not just the evolution rules restated in prose
(§10.4). The concrete proof this repo implements:
`libs/engine/domain-core/contracts/fixtures/command_v1.fbs` is a frozen,
byte-for-byte copy of `contracts/command.fbs` as it stood before
`Increment` gained a new field (`sequence_hint`). A test
(`tests/flatbuffers_evolution.rs`) encodes a message with the *old*
schema's generated Rust code and decodes it with the *current* schema's
generated code (and the reverse direction), proving §10.4's backward/
forward-compatibility guarantees hold for real, against two genuinely
different generated schemas.

That old schema's generated Rust code
(`libs/engine/domain-core/tests/generated_v1/command_v1_generated.rs`)
is not "always reproducible" in the sense §10.3's default rule assumes:
nobody regenerates a frozen historical fixture as part of normal
iteration (running `nx run engine-domain-core:generate` only
ever touches the *current* schemas, never `fixtures/command_v1.fbs`) --
if this generated file were gitignored like the live schemas' output,
a fresh clone would be missing it with no command that reproduces it,
breaking the evolution test for anyone but whoever manually re-ran
`flatc` against the fixture by hand.

## Options considered

1. **Gitignore it like the live schemas' output** (§10.3's default).
   Rejected: not actually reproducible by any existing command, so this
   would silently break the evolution test for a fresh clone/CI --
   exactly the kind of "generated code that's supposed to exist before
   use" §10.3 is worried about, just for a fixture nothing else
   regenerates.
2. **Add a dedicated Nx target that regenerates the v1 fixture too**,
   alongside the live schemas. Rejected as unnecessary ceremony: the
   fixture is deliberately static forever (a "v2" fixture, if ever
   needed, would be a new frozen file, not a regeneration of this one) --
   wiring live codegen for something that must never actually change
   adds a target whose only job is to never do anything different.
3. **Commit the v1-generated code directly**, invoking §10.3's own
   documented exception. **Recommended.** The generated file becomes
   real, versioned source for a fixture that is itself frozen source --
   consistent with the fixture's own nature, no phantom regeneration
   step, and exactly the scenario §10.3's exception clause anticipates
   ("a consumer ... requires committed code").

## Recommendation

Option 3. `libs/engine/domain-core/tests/generated_v1/command_v1_generated.rs`
is committed alongside `contracts/fixtures/command_v1.fbs`, both treated
as frozen historical source, never regenerated by the normal
`engine-domain-core:generate` Nx target. `codegen:check` (§10.3's own
validation companion to this exception) isn't a separate tool in this
repo yet -- the equivalent check today is `cargo test -p
grafting-domain-core --test flatbuffers_evolution`, which would fail
loudly if the committed fixture code and the frozen `.fbs` it was
generated from ever drifted apart.

## Risks

- If `flatc`'s Rust codegen output format changes in a future toolchain
  upgrade, this one committed file won't automatically match what a
  *new* `flatc` run would produce from the same `.fbs` -- not a
  practical problem (the fixture is never regenerated on purpose), but
  worth noting so a future reader doesn't assume this file tracks the
  currently-pinned `flatc` version the way the live `src/generated/`
  output does.
- A second "v2" fixture, if this evolution test is ever extended to
  prove a longer chain, would need the same treatment (frozen `.fbs` +
  committed generated code) -- not automated, a manual step each time.
